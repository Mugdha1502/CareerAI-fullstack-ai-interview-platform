# Backend deployment notes

Notes for running the CareerAI Spring Boot backend outside a developer machine. Nothing here has been deployed yet.
For the step-by-step hosting walkthrough see [deployment-guide.md](deployment-guide.md).

## 1. Profile and required variables

Run the deployed backend with `SPRING_PROFILES_ACTIVE=prod`. The `prod` profile has **no local defaults**: if a required variable is missing, the app stops at startup instead of falling back to localhost or a development value.

| Variable | Required | Notes |
|---|---|---|
| `SPRING_PROFILES_ACTIVE` | Yes | `prod` |
| `DB_URL` | Yes | e.g. `jdbc:mysql://host:3306/careerai?sslMode=REQUIRED&serverTimezone=UTC` |
| `DB_USERNAME`, `DB_PASSWORD` | Yes | Use a database user that is not `root` |
| `JWT_SECRET` | Yes | 32+ random bytes. Missing, short, low-variety or publicly known values are refused |
| `CORS_ALLOWED_ORIGINS` | Yes | Exact frontend origin(s), e.g. `https://careerai.example.com`. Wildcards are refused |
| `TRUSTED_PROXIES` | When behind a proxy | IPs/CIDR ranges of the host's reverse proxy (see section 3) |
| `RESUME_STORAGE_PROVIDER` | Optional | `database` (prod default) or `local` with `RESUME_STORAGE_DIR` on a persistent disk |
| `FLYWAY_BASELINE_ON_MIGRATE` | Once, for an existing database | `true` for one start only (section 5). Default `false` |
| `PORT` / `SERVER_PORT` | Optional | Usually provided by the host |
| `DB_POOL_SIZE` | Optional | Connection pool size (default 5; managed MySQL plans allow few connections) |
| `GEMINI_API_KEY`, `SIMLI_API_KEY`, `JDOODLE_CLIENT_ID`, `JDOODLE_CLIENT_SECRET` | Optional | Features report "unavailable" without them |
| `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET` | Optional | Test Mode keys only |

Generate a JWT secret, for example: `openssl rand -base64 48`.

`application-local.properties` is excluded from the built JAR, so local secrets never ship.

## 2. Login rate limiting

- Failed logins are counted per **account + client IP** (default 5 per 15 minutes) and per **client IP** across accounts (default 30 per 15 minutes). Over the limit the API answers `429 LOGIN_RATE_LIMITED` with a `Retry-After` header.
- Unknown emails and wrong passwords get the same response, the same timing and the same limits.
- A successful login clears that account + IP counter.
- **Counters are in memory, per backend instance.** With more than one instance, each keeps its own counters (an attacker gets N× the attempts). For multiple instances, move the counters to a shared store (Redis with a sliding window or Bucket4j, or a database table).

## 3. Reverse proxies and client IPs

`X-Forwarded-For` is ignored unless the direct peer is listed in `TRUSTED_PROXIES`. When it is trusted, the header is read from the right, skipping trusted hops, so a value typed by the client is never used.

If the backend runs behind a proxy and `TRUSTED_PROXIES` is not set, all requests appear to come from the proxy. The backend logs a warning once and skips the per-IP limit for those requests (the account + IP limit still applies), so one attacker cannot block every user.

## 4. Resume storage

- `local`: files under `RESUME_STORAGE_DIR`. Only persistent if that folder is on a mounted disk/volume.
- `database`: bytes in the `resume_file_blobs` table (max 5 MB per file). Works on hosts with an ephemeral filesystem.
- Existing `resumes.storage_path` values are unchanged by either provider. With `database`, older local files remain readable while `RESUME_STORAGE_LOCAL_FALLBACK=true`.
- Storage paths are generated by the server (`{userId}/{random}.{pdf|doc|docx}`) and validated before every read, write and delete. Downloads are owner-only.

## 5. Database schema and migrations (Flyway)

Flyway 12.4 (managed by Spring Boot 4.1) runs the versioned scripts in `careerai-backend/src/main/resources/db/migration`:

| Script | Contents |
|---|---|
| `V1__baseline_schema.sql` | The 19 tables that existed before the database storage provider, in foreign-key order, with all primary keys, unique keys, indexes, foreign keys and check constraints |
| `V2__resume_file_blobs.sql` | `resume_file_blobs` (`CREATE TABLE IF NOT EXISTS`, additive only) |

V1 was generated from the JPA entities on MySQL 8.0 and compared with the existing development database: identical tables, columns, keys and constraints. A test (`MigrationCoverageTest`) fails if an entity maps a table or column that no migration creates.

Behaviour by profile:

- **Local development (default):** `ddl-auto=update`, Flyway **off** (`FLYWAY_ENABLED=false`). A developer database is never migrated automatically.
- **prod:** Flyway **on**, then `ddl-auto=validate` (Hibernate only checks the schema, never changes it). `clean` is disabled. Flyway refuses to touch a non-empty database that has no `flyway_schema_history` table unless baselining is explicitly enabled.

### 5.1 New, empty database

Create an empty MySQL 8 database (utf8mb4) and start the backend with the prod profile. Flyway applies V1 and V2, Hibernate validates, the app starts. Nothing else is needed.

### 5.2 Existing database created before Flyway (for example the local `careerai`)

Do this once, during a quiet period:

1. **Back up first** and keep the file somewhere safe:
   `mysqldump --single-transaction --routines --triggers --no-tablespaces -u <user> -p careerai > careerai-backup-YYYYMMDD.sql`
2. **Rehearse on a copy:** restore the backup into a scratch database (`CREATE DATABASE careerai_rehearsal; mysql ... careerai_rehearsal < backup.sql`) and start the prod profile against it with `FLYWAY_BASELINE_ON_MIGRATE=true`. Expected log lines: `Successfully baselined schema with version: 1`, `Migrating ... to version "2"`, `Started CareeraiBackendApplication`, and `/actuator/health` = `UP`. If Hibernate validation fails, stop: the schema differs from the entities and needs a reviewed migration first.
3. **Run it for real** with the same setting for **one** start: V1 is only *recorded* as applied (never executed), and V2 creates `resume_file_blobs` only if it is missing. No table is dropped, recreated or altered, and no row is changed.
4. **Remove** `FLYWAY_BASELINE_ON_MIGRATE` (or set it to `false`) and restart. Flyway should report `Successfully validated 3 migrations`.
5. **Verify:** `SELECT version, type, success FROM flyway_schema_history;` shows `1 BASELINE` and `2 SQL`, both successful; row counts match the backup.

Never run `flyway clean`, `repair` or `baseline` by hand against a real database without a fresh backup.

Restoring if something goes wrong: stop the app, `DROP DATABASE careerai; CREATE DATABASE careerai;`, restore the backup with `mysql ... careerai < careerai-backup-YYYYMMDD.sql`.

### 5.3 Future schema changes

Every entity change gets a new reviewed script (`V3__describe_change.sql`, …), tested first on a disposable database. Never edit a script that has already run anywhere: Flyway checks their checksums at startup.

### 5.4 Risks

- Scripts use MySQL 8 syntax and the `utf8mb4_0900_ai_ci` collation; MariaDB or other MySQL-compatible services may need adjustments.
- A database whose schema was changed by hand (columns dropped/renamed) will fail Hibernate validation after baselining. That is intended: the app refuses to start instead of writing to a wrong schema.
- `FLYWAY_BASELINE_ON_MIGRATE=true` left on permanently is not harmful for an already-baselined database, but turn it off so a wrong database URL is never baselined by accident.
